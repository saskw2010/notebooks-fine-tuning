MK7 Native MoE — Research Story

From large-model expert streaming experiments to a native sparse MoE designed for local inference.

1. Why this experiment exists

The starting observation came from running very large sparse models through Colibrì-style expert streaming: a model can be much larger than local VRAM if only the routed experts are fetched when needed. The useful idea was not merely “offload a huge model”; it was to ask whether a model could be designed from the beginning so its architecture and runtime cooperate with tiered expert residency.

That led to the MK7 Native MoE experiment: a causal Transformer with routed feed-forward experts, a streamable expert boundary, and an explicit long-term goal of separating total capacity from active compute per token.

2. Architectural thesis

token
  ↓
causal attention / shared trunk
  ↓
router
  ↓ Top-2
selected experts
  ↓
merge
  ↓
next layer / logits

For inference, the intended residency path is:

router → expert IDs → tier manager → VRAM / RAM / NVMe → selected experts

The important distinction is that sparse MoE is the model architecture, while expert streaming is an inference/runtime technique. The model is being shaped so the two can fit together, without making training depend on NVMe paging.

3. What has actually been implemented

  • Causal Transformer language model.
  • RMSNorm and causal self-attention.
  • SwiGLU feed-forward experts.
  • Configurable sparse Top-k router.
  • Research default: 8 experts, Top-2.
  • Router load-balancing auxiliary loss.
  • Capacity/drop accounting and expert-load metrics.
  • ExpertStore abstraction.
  • File-backed lazy expert loading with bounded LRU cache as a proof of the streamable boundary.
  • Kaggle/Colab runnable notebook and GitHub→Kaggle automation work.

4. First real GPU validation — Kaggle T4

The first research-scale preset was:

ItemValue
Total parameters28,697,760
Approx. active parameters/token8,791,200
Experts8
RoutingTop-2
Transformer layers6
d_model288
Expert hidden size640
Sequence length256

The successful 100-step run used a Tesla T4. The loss moved from 5.6069 at step 1 to 1.2943 at step 100. LM loss moved from 5.5932 to 1.2836. Router auxiliary loss moved from 1.3771 to 1.0656. Dropped assignments fell from 2391 to 440. All eight experts continued receiving traffic.

Interpretation: this is an architecture/routing validation, not a language-quality benchmark. The corpus used for this run was intentionally tiny and repetitive, so the falling loss mostly proves that the end-to-end sparse model learns and that the router does not immediately collapse.

5. Hardware lesson learned

Kaggle's current PyTorch image rejected Tesla P100 execution because the installed build supported CUDA compute capability sm_70+, while P100 is sm_60. The same experiment then succeeded on Tesla T4 (sm_75). This was an environment compatibility issue, not an MoE failure.

6. Current target

The longer-term target remains approximately:

1.5–3B total parameters
300–500M active parameters/token
8–16 routed experts
Top-2 routing
optional shared experts
quantized experts
streamable expert residency
optional LoRA/adapters on top of experts

The central objective is not to make a 300–500M total model. It is to build a model whose active compute is in that range while total representational capacity is substantially larger.

7. Research note — PrismML Bonsai 27B

external researchlow-bit models

PrismML announced Bonsai 27B in July 2026, based on Qwen3.6 27B, with binary and ternary variants. PrismML reports a 1-bit/binary variant at about 3.9 GB and a ternary variant at about 5.9 GB. The company reports 1.125 effective bits/weight for the binary model and 1.71 effective bits/weight for the ternary model, with benchmark retention reported relative to the FP16 baseline.

PrismML also describes the family as supporting multimodal input, tool use, reasoning/agentic workflows and long context. These are vendor-reported results and should be independently reproduced before using them as engineering assumptions.

Why Bonsai matters to MK7

Bonsai attacks the local-inference problem from a different axis:

Colibrì / MK7 streaming idea → reduce resident weights by loading only selected experts
Bonsai idea                 → reduce bytes per weight extremely aggressively

The interesting research direction is their combination. If routed experts can be trained or converted to binary/ternary representations while router/shared components retain higher precision, total local capacity could grow dramatically before NVMe traffic becomes the dominant bottleneck.

Questions to test later

  • Can expert FFNs tolerate 1–2 bit weights better than attention/router components?
  • Should the router remain FP16/BF16 while experts become ternary/binary?
  • What is the real runtime RAM/VRAM footprint, not only file/weight size?
  • What kernels are required for low-bit speedups, and do they work on commodity GPUs/CPUs/mobile NPUs?
  • Does extreme low-bit compression damage expert specialization or routing stability?

Source: PrismML — Bonsai 27B announcement.

8. Research note — AllenAI olmOCR

external researchdocument intelligencetraining data

olmOCR is AllenAI's open-source toolkit for converting PDFs and image-based documents into clean, naturally ordered text/Markdown for LLM datasets and downstream processing. The project handles complex layouts, tables, equations, handwriting, headers/footers, multi-column pages and reading-order reconstruction.

The original olmOCR work used a fine-tuned 7B vision-language model and released weights, data, training code and inference tooling. The later olmOCR 2 work uses reinforcement learning with verifiable rewards derived from unit tests generated from synthetic documents with known structure. AllenAI reports especially strong improvements on equations, tables and multi-column layouts.

Why olmOCR matters to MK7

olmOCR is not a competing MoE runtime. Its relevance is upstream: high-quality document linearization can become part of the data factory used to train or distill domain experts.

PDF / scan / image
      ↓
olmOCR-style document linearization
      ↓
clean Markdown / structured text
      ↓
filter + deduplicate + chunk + labels
      ↓
teacher expansion / synthetic QA / tool traces
      ↓
expert-specific training datasets
      ↓
MK7 experts + router training

This is especially relevant for ERP manuals, policies, invoices, technical documents, Arabic business content and other document-heavy domains. The real value is not “OCR text extraction” alone; it is producing training-grade representations with reading order and structure preserved.

Possible integration experiments

  • Use olmOCR output as one ingestion path for expert datasets.
  • Evaluate Arabic and mixed Arabic/English documents separately; olmOCR's published benchmark emphasis is primarily English, so Arabic quality must be measured rather than assumed.
  • Generate routing labels from document type/domain metadata.
  • Train a document expert and compare it against RAG-only use of the same extracted corpus.
  • Reuse the unit-test/reward idea from olmOCR 2 for verifiable structured-output training in ERP/document tasks.

Sources: AllenAI olmOCR repository, olmOCR paper, and olmOCR 2 paper.
